コマンド (48 スラッシュコマンド)
CLAUDE.md で定義されたワークフロートリガー。状況に合わせて使い分ける。

🏗️ 開発の基本サイクル

/plan
実装計画の作成

複雑な機能を段階的なフェーズに分解し、実装前に全体像を把握する。コーディング開始前に必ず実行することで手戻りを防ぐ。

WHEN ・新機能の実装前
・リファクタリング計画
・要件が曖昧なとき
・複数コンポーネントにまたがる変更
AGENT planner (Opus)
NEXT 計画確認後 → /tdd or /orchestrate
/tdd
テスト駆動開発 (TDD)

テスト先行でコードを書く。RED → GREEN → REFACTOR のサイクルを強制。カバレッジ80%以上を目標とする。

WHEN ・新機能実装時（常に）
・バグ修正時（再現テストを先に書く）
・リファクタリング前（既存テスト確認）
AGENT tdd-guide (Sonnet)
NEXT 実装完了後 → /code-review
/code-review
コード品質・セキュリティレビュー

OWASP Top 10 を含むセキュリティ検査 + コード品質チェック。コミット前の最終確認として使う。CRITICAL/HIGH の問題があればマージ不可。

WHEN ・コード変更後、コミット前（常に）
・認証・決済・API エンドポイント変更時は必須
・PR 作成前
AGENT code-reviewer + security-reviewer
NEXT 問題なし → /verify → git commit
/verify
総合品質ゲート検証

ビルド・型チェック・lint・テスト・カバレッジ・シークレット検出を一括実行。PR 前の最終チェックポイント。

サブコマンド:
/verify quick   ← ビルド + 型チェックのみ（高速）
/verify pre-pr  ← 全項目（PR前）
/verify full    ← セキュリティスキャン含む全項目
WHEN ・PR 作成前（必須）
・大きな変更後
・ビルドエラー確認後
SKILL verification-loop
/e2e
E2E テスト生成・実行

Playwright を使って重要なユーザーフローのE2Eテストを自動生成・実行する。失敗時はスクリーンショットと HTML レポートを保存。

WHEN ・ログイン・決済などクリティカルフロー
・リリース前の回帰テスト
・マルチステップのUXテスト
AGENT e2e-runner
SKILL e2e-testing
/build-fix
ビルド・型エラーの段階的修正

コンパイルエラーや型エラーをひとつずつ順番に修正する。エラーが多数あっても焦らず確実に直す。

WHEN ・ビルドが失敗したとき（即座に）
・型エラーが大量発生したとき
・リファクタリング後の型整合性修正
AGENT build-error-resolver

🎭 オーケストレーション

/orchestrate
マルチエージェント順次実行

planner → tdd-guide → code-reviewer → security-reviewer の順でエージェントを連鎖させる。1コマンドでフル開発サイクルを実行。

例:
/orchestrate feature "ユーザー認証機能"
/orchestrate bugfix "決済処理のNullエラー"
/orchestrate refactor "Serviceクラスを分離"
WHEN ・中〜大規模の機能実装
・複数の視点が必要な変更
・セキュリティクリティカルな実装
AGENT planner tdd-guide code-reviewer security-reviewer
/multi-plan
マルチモデル協調計画

Claude + Codex + Gemini が並列に同じ問題を分析し、最良の計画に統合。複数AIの視点を合成する。

フロー:
/multi-plan "決済モジュール追加"
  → 各モデルが並列に分析
  → 結果を合成
  → /multi-execute で並列実装
WHEN ・フルスタック機能（BE+FE同時）
・アーキテクチャ決定が重要な場面
・複数の実装方針を比較したいとき
NEXT 計画確認後 → /multi-execute

🔄 自律ループ

/loop-start
自律開発ループの開始

バックログからタスクを自動処理し、テスト・品質ゲート通過後に自動コミット・PR作成を繰り返す。危険度：中（品質ゲートで自動停止するが監視必須）。

モード:
--mode safe          ← 推奨。品質ゲート厳格
--mode continuous-pr ← 自動PRを継続生成
--mode rfc-dag       ← RFC形式で依存管理
--mode infinite      ← 無限ループ（上級者向け）
WHEN ・明確なバックログがあるとき
・単純なタスクが大量にあるとき
・深夜の自動処理（朝確認）
MONITOR /loop-status で状況確認
AGENT loop-operator
/quality-gate
品質ゲートの手動実行

ビルド成功・テストカバレッジ80%以上・lint通過・シークレット未検出を一括確認。ループ内でも手動でも使う。

WHEN ・自律ループのチェックポイント
・コミット前の最終確認
・CI/CD 前のローカル検証

🧠 学習・知識管理

/learn
セッションからパターン抽出

難しい問題を解決した後、そのアプローチをスキルとして保存する。次のセッションで自動的に使える。チームの暗黙知を形式知に変える。

WHEN ・難しいバグを直したとき
・新しい回避策を発見したとき
・プロジェクト固有の規約を学んだとき
SKILL continuous-learning continuous-learning-v2
RELATED /instinct-status /skill-create
/refactor-clean
デッドコードの安全な削除

未使用コード・依存を検出し、1件ずつ削除してテスト確認するサイクルを繰り返す。誤削除時は自動リバート。

WHEN ・コードが肥大化してきたとき
・リファクタリング後の整理
・依存関係のクリーンアップ
AGENT refactor-cleaner

🪝
フック (自動イベント駆動)
明示的に呼ばなくても自動的に実行される。hooks.json で定義。
⚙️ フック制御
# 厳格度を変更
export ECC_HOOK_PROFILE=minimal   # 最小限
export ECC_HOOK_PROFILE=standard  # 標準（デフォルト）
export ECC_HOOK_PROFILE=strict    # 厳格

# 特定フックを無効化
export ECC_DISABLED_HOOKS="doc-file-warning,tmux-reminder"

# セキュリティ監視を有効化（オプション）
export ECC_ENABLE_INSAITS=1
フックの種類

PreToolUse — ツール実行前に介入。中断も可能。

PostToolUse — ツール実行後に処理。整形・ログ・分析。

SessionStart — セッション開始時に前回コンテキストを復元。

PreCompact — コンテキスト圧縮前にセッション状態を保存。

Stop — セッション終了時にパターン抽出・コスト集計。

実践ワークフロー
シチュエーション別のコマンド・エージェント・フックの組み合わせ方。
1
標準機能開発（TDD）
新機能追加のゴールデンパス。全ての機能開発はここから始める。
/plan "機能の説明"
→ planner (Opus) が実装フェーズを設計
→ 計画を確認・承認してから次へ
/tdd "計画に基づいて実装"
→ tdd-guide (Sonnet) が RED→GREEN→REFACTOR
→ post-edit-format フックが自動フォーマット
→ カバレッジ 80% 達成まで継続
/code-review
→ code-reviewer + security-reviewer
→ CRITICAL/HIGH があれば修正して再実行
/verify pre-pr
→ ビルド・型・lint・テスト・シークレット検査
git add / commit / push
→ git-push-reminder フックが変更内容を確認
→ pr-created フックが PR URL をログ
2
バグ修正（高速サイクル）
再現テスト → 修正 → 確認。最短で完了させる。
/orchestrate bugfix "バグの説明"
一括で以下を実行:
planner: 原因分析・修正計画
tdd-guide: 再現テスト作成 → 修正 → 通過確認
code-reviewer: 修正コードのレビュー
/verify quick
→ ビルド + 型チェックのみ（高速）
git commit / push
→ /learn で解決パターンを保存（任意）
3
セキュリティクリティカルな実装
認証・決済・API など。セキュリティを最優先にするフロー。
/plan "セキュリティ要件を含む機能"
→ セキュリティ考慮事項を計画に含める
/tdd （セキュリティテスト先行）
→ 認証バイパス・入力検証・SQLインジェクションのテストを先に書く
/code-review （セキュリティフォーカス）
→ security-reviewer が OWASP Top 10 スキャン
→ CRITICAL が1つでもあれば即座に修正・再レビュー
/verify full
→ セキュリティスキャン含む全項目チェック
4
大規模リファクタリング
安全に・段階的に・テストを壊さずリファクタリングする。
/plan "リファクタリングの目的と範囲"
→ 変更範囲・影響箇所を明確にしてから着手
/orchestrate refactor "リファクタリング"
→ architect: 新構造を設計
→ tdd-guide: 既存テストが全て通ることを確認
→ code-reviewer: リファクタリング品質チェック
/refactor-clean （オプション）
→ refactor-cleaner: デッドコードを1件ずつ安全に削除
→ 削除後テスト → 失敗したら自動リバート
/verify full
→ 全項目確認後にコミット
5
自律開発ループ
バックログを自動消化。夜間処理・定型タスクの自動化。
/loop-start continuous-pr --mode safe
→ ベースラインテストを確認
→ バックログからタスクを自動選択
【自動ループ内】
/plan → /orchestrate → /quality-gate
通過: 自動コミット → 自動PR作成
失敗: loop-operator が介入・停止
/loop-status
→ 定期的に確認。品質ゲート失敗で自動停止。
→ 監視必須 完全放置は非推奨
6
知識の蓄積と継続改善
解決した問題を再利用可能な知識に変える。チーム全体の生産性を上げる。
難しい問題を解決する
→ continuous-learning-observe フックが自動記録
/learn （即時）または セッション終了を待つ
→ Stop フックが自動的にパターン抽出・評価
→ ~/.claude/skills/learned/ に保存
/instinct-status で確認
→ 学習済みスキルの一覧・信頼度を確認
/skill-create （高度）
→ git 履歴からチーム固有のパターンを自動抽出
→ 新スキルとして登録 → 次回から自動適用

🏆 成功のための 7 原則

1️⃣
複雑な機能は必ず /plan から
手戻りを防ぐ最大の武器。計画なしにコーディングを始めない。
2️⃣
常にテストを先に書く
TDD はオプションではなくデフォルト。バグ修正でも再現テストを先に。
3️⃣
コミット前に必ず /code-review
セキュリティ問題は後から直すほど高コスト。早期発見が命。
4️⃣
PR前に /verify pre-pr
CI が落ちてから直すより、ローカルで先に確認する方が速い。
5️⃣
専門エージェントに委譲する
汎用的な指示より、/orchestrate や専門コマンドの方が品質が高い。
6️⃣
/loop-status で自律ループを監視
完全放置は危険。品質ゲートは自動停止するが定期確認を怠らない。
7️⃣
/learn でチームの知識を蓄積
解決したパターンを保存するだけで、未来の自分とチームが助かる。
