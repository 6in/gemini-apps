GSD コマンド チートシート

meta-prompting & context engineering による spec-driven 開発システム。
v1.36.0 の 73 コマンドから 81 コマンドに拡張。スパイク・スケッチ・スペック精査・GitHub インボックス・ドキュメント取り込みなど大幅強化。

まずはこれで判定

今すぐ実装しない → /gsd:add-todo or /gsd:note
超小さい修正（計画不要） → /gsd:fast
今やる小変更 → /gsd:quick
小さいが先に仕様確認したい → /gsd:quick --discuss
小さいが品質保証もほしい → /gsd:quick --full
どのコマンドか迷っている → /gsd:do [やりたいこと]
アイデアを練りたい・方向性を確認したい → /gsd:explore
技術的実現性を先に確認したい → /gsd:spike [idea]
UI デザインをラフに探索したい → /gsd:sketch [idea]
フェーズ要件が曖昧・仕様を固めてから計画したい → /gsd:spec-phase [N]
独立した新機能を末尾に追加 → /gsd:add-phase
既存計画の途中に urgent work を差し込む → /gsd:insert-phase [N]
phase の方針が曖昧 → /gsd:discuss-phase [N] → /gsd:plan-phase [N]
何かが壊れた → /gsd:debug [desc]
次に何をすべきか不明 → /gsd:next

3つの見分け方

  • いま着手するか？ しないなら add-todo / note。
  • 局所修正か、独立機能か？ 局所修正なら quick（または fast）、独立機能なら add-phase。
  • 順番を壊す必要があるか？ 途中差し込みなら insert-phase。
quick のフラグ使い分け:
• フラグなし — 最速で実装（バグ修正・設定変更向き）
• --discuss — 事前に仕様確認してから実装
• --research — 実装アプローチを事前調査
• --validate — plan-check + verification のみ有効（discussion なし）
• --full — discussion + research + plan-check + verification すべて有効
• フラグは組み合わせ可: --discuss --research --validate = --full
fast vs quick:
• fast — サブエージェントなし・計画なし。コメント追加・変数名変更レベルの trivial な修正に。
• quick — planner + executor を起動。小〜中規模の実際の変更に。
spike vs sketch:
• spike — 技術的実現性を確認する使い捨て実験。「これは動くか？」を検証。
• sketch — UI デザインの方向性を探索する使い捨てモックアップ。「これは見えるか？」を探索。
どちらも -wrap-up で findings を永続スキルとして保存できる。
add-phase vs insert-phase:
• add-phase — ロードマップ末尾に整数番号で追加。今の流れを壊さない。
• insert-phase — 途中に小数番号（例: 3.1）で差し込み。後続を renumber しない。

スパイク & スケッチ

NEW in v1.37
コマンド用途主な引数
/gsd:spike NEW技術的実現性を確認する使い捨て実験。仮説を検証し findings を記録（.planning/spikes/）<idea> [--quick]
/gsd:spike-wrap-up NEWスパイク実験の findings を永続プロジェクトスキルとしてパッケージ化し、将来のビルド会話で自動ロード—
/gsd:sketch NEW使い捨て HTML モックアップで UI デザインの方向性を探索。2〜3 バリアントを生成して比較（.planning/sketches/）<design idea> [--quick]
/gsd:sketch-wrap-up NEWスケッチデザインの findings を永続プロジェクトスキルとしてパッケージ化し、本実装時に自動ロード—
使い方の流れ:
spike → 実験 → spike-wrap-up → findings がスキルとして保存 → 本実装時に自動ロード
sketch → モックアップ → sketch-wrap-up → デザイン決定がスキルとして保存 → UI 実装時に自動ロード
--quick フラグでインテーク質問をスキップして直接構築に入れる。

plan-phase のエージェント構成

/gsd:plan-phase N
  ├── Phase Researcher (×4 並列)
  │    ├── Stack / Features
  │    ├── Architecture / Pitfalls
  │    └── → RESEARCH.md
  ├── Planner
  │    └── → PLAN.md (XML 構造)
  └── Plan Checker (最大 3 回ループ)
       └── PASS → 完了 / FAIL → 修正

新フラグ:
  --tdd  → TDD モードで計画生成
  --gaps → ギャップのみ再計画
  --reviews → 外部レビューを考慮

execute-phase のウェーブ実行

/gsd:execute-phase N
  ├── 依存関係分析
  ├── Wave 1 (独立プラン並列)
  │    ├── Executor A → commit
  │    └── Executor B → commit
  ├── Wave 2 (Wave 1 に依存)
  │    └── Executor C → commit
  └── Verifier
       └── PASS / FAIL → VERIFICATION.md

新フラグ:
  --tdd        → TDD モードで実行
  --wave N     → 特定 wave から再開
  --interactive → 各タスク前に確認

各 Executor は新鮮な 200K コンテキストで実行。

spec-phase の仕様精査フロー

/gsd:spec-phase N
  ├── コードベーススカウト
  ├── ソクラテス式対話 (最大6ラウンド)
  │    └── 4次元で曖昧度スコアリング
  ├── ゲート: 曖昧度 ≤ 0.20 かつ
  │          全次元最小値を満たす
  └── → SPEC.md（偽造不可能な要件）
       └── discuss-phase が自動ロード

--auto  → 推奨デフォルトで自動決定
--text  → テキスト形式で出力

spike / sketch のフロー

/gsd:spike "アイデア"
  ├── 実験分解 → リスク順実行
  ├── 検証 → .planning/spikes/ に記録
  └── /gsd:spike-wrap-up
       └── .claude/skills/spike-findings/
            → 将来のビルドで自動ロード

/gsd:sketch "UI アイデア"
  ├── モード確認 → 2〜3バリアント生成
  ├── HTML モックアップ比較
  └── /gsd:sketch-wrap-up
       └── .claude/skills/sketch-findings/
            → UI フェーズで自動ロード

discuss-phase の新フラグ

/gsd:discuss-phase N
  --auto   → 推奨デフォルトで自動決定
  --chain  → 対話後に plan+execute を自動実行
  --batch  → ファイルベース UI で質問バッチ処理
  --power  → 全質問を一括生成（自分のペースで回答）
  --analyze → 想定を分析して表示
  --text   → テキスト形式で出力

判断基準:
- trivial な修正（コメント・変数名）か → fast

- 品質保証（全パイプライン）が必要か → --full
- 独立した新機能か → add-phase
- 既存ロードマップの途中に差し込む必要があるか → insert-phase
- 今すぐ実装するか、後で検討するだけか → add-todo / note
- 何かが壊れているか → debug
- どのコマンドか迷っているか → do
- アイデアを練りたいか → explore
- 技術的実現性を先に確認したいか → spike
- UI デザインの方向性を先に探りたいか → sketch
- フェーズ要件が曖昧・仕様を先に固めたいか → spec-phase
- AI 機能を組み込むか → ai-integration-phase
- フロントエンドフェーズか → ui-phase
- 実装完了して PR を出すか → ship
- GitHub の issues/PR を整理したいか → inbox
- 既存 ADR/PRD/SPEC から .planning/ を初期化したいか → ingest-docs

注意点

execute-phase をやり直さない。 実装後に少し変えたいなら /gsd:quick、体系的に問題を洗いたいなら /gsd:verify-work を使う。
trivial な修正に quick を使わない。 コメント追加・変数名変更レベルなら /gsd:fast で十分。quick はサブエージェントを起動するのでコストがかかる。
  • 計画がズレていると感じたら /gsd:discuss-phase [N] を挟んでから re-plan。
  • フェーズ要件が曖昧なら /gsd:spec-phase [N] で discuss 前に仕様精査。
  • 技術的に動くか不安なら /gsd:spike で先に実験。/gsd:spike-wrap-up で findings を永続化。
  • UI の方向性が決まっていないなら /gsd:sketch で先にモックアップ探索。/gsd:sketch-wrap-up で設計を永続化。
  • セッションをまたぐなら /gsd:progress → /gsd:resume-work → /gsd:next（次を自動判定）。
  • コンテキスト品質が落ちたら /clear してから /gsd:resume-work。
  • 既存コードベースで初めて GSD を使う場合は /gsd:scan → /gsd:map-codebase → /gsd:new-project。
  • 既存の ADR/PRD/SPEC がある場合は /gsd:ingest-docs で .planning/ を自動生成（最大50ドキュメント、ADR優先）。
  • プランが大きすぎると stub になる。タスクは 2-3 個が目安。
  • コスト削減: /gsd:set-profile budget + /gsd:settings で research / plan_check をオフ。
  • アップデート後にローカル変更が消えたら /gsd:reapply-patches。
  • .planning/ をバージョン管理したくない場合は commit_docs: false + .gitignore に追加。
  • フェーズをロールバックしたいなら /gsd:undo <phase>（依存チェック付き）。
  • PR を出すときは /gsd:pr-branch で .planning/ コミットを除外したクリーンブランチを作成。
  • /gsd:ultraplan-phase BETA は Claude Code v2.1.91+ が必要。安定版は /gsd:plan-phase。
