GSD Core コマンド チートシート

meta-prompting & context engineering による spec-driven 開発システム。
67 コマンド（旧 gsd-build v1.38.1 の 81 から CRUD 系を統合してスリム化、コマンド面は redux 1.1.0 と同等）。
2 段階 namespace routing（6 個の ns-* メタスキル）でモデルの cold-start 負荷を大幅軽減。
2 回のリブランドと SDK 統合があるため、v1.38 系または redux 系から移行する場合は 移行表 を参照。

Project Continuity Notice — 2026-04 以降、旧アップストリーム gsd-build/get-shit-done（メンテナ TÂCHES）が連絡不能となり、$GSD トークン絡みの rug-pull 疑惑も公表されました。コミュニティが立ち上げたフォーク open-gsd/get-shit-done-redux（メンテナ trek-e）が後継として開発を継続。さらに 2026-05-29 に open-gsd/gsd-core へ改名され、npm パッケージ・install binary も gsd-core 系に切替（改名コミット #518）。
パッケージ名の変遷: get-shit-done-cc → @opengsd/get-shit-done-redux → @opengsd/gsd-core。install binary: get-shit-done-cc → get-shit-done-redux → gsd-core。SDK @gsd-build/sdk → @opengsd/gsd-sdk は ADR-0174 により本体に統合・廃止。

まずはこれで判定

今すぐ実装しない → /gsd:capture（note/backlog/seed 統合）
超小さい修正（計画不要） → /gsd:fast
今やる小変更 → /gsd:quick
小さいが先に仕様確認したい → /gsd:quick --discuss
小さいが品質保証もほしい → /gsd:quick --full
どのコマンドか迷っている → /gsd:progress --do "..." REDUX
アイデアを練りたい・方向性を確認したい → /gsd:explore
技術的実現性を先に確認したい → /gsd:spike [idea]
UI デザインをラフに探索したい → /gsd:sketch [idea]
フェーズ要件が曖昧・仕様を固めてから計画したい → /gsd:spec-phase [N]
MVP の縦切りスライスで進めたい → /gsd:mvp-phase [N] REDUX
新フェーズを追加・差し込み・編集・削除 → /gsd:phase [--insert|--remove|--edit] REDUX
phase の方針が曖昧 → /gsd:discuss-phase [N] → /gsd:plan-phase [N]
他 AI とプランをすり合わせたい → /gsd:plan-review-convergence [N] REDUX
何かが壊れた → /gsd:debug [desc]
次に何をすべきか不明 → /gsd:progress --next REDUX

3つの見分け方

  • いま着手するか？ しないなら /gsd:capture。
  • 局所修正か、独立機能か？ 局所修正なら quick（または fast）、独立機能なら phase。
  • 順番を壊す必要があるか？ 途中差し込みなら phase --insert。
quick のフラグ使い分け:
• フラグなし — 最速で実装（バグ修正・設定変更向き）
• --discuss — 事前に仕様確認してから実装
• --research — 実装アプローチを事前調査
• --validate — plan-check + verification のみ有効（discussion なし）
• --full — discussion + research + plan-check + verification すべて有効
• フラグは組み合わせ可: --discuss --research --validate = --full
fast vs quick:
• fast — サブエージェントなし・計画なし。コメント追加・変数名変更レベルの trivial な修正に。
• quick — planner + executor を起動。小〜中規模の実際の変更に。
spike vs sketch (redux: wrap-up はフラグ化):
• spike — 技術的実現性を確認する使い捨て実験。「これは動くか？」を検証。
• sketch — UI デザインの方向性を探索する使い捨てモックアップ。「これは見えるか？」を探索。
• 完了したら spike --wrap-up / sketch --wrap-up で findings をプロジェクトスキルに永続化（旧 -wrap-up サブコマンドは削除）。
phase コマンドの使い分け（redux 統合）:
• phase <desc> — 末尾追加（旧 add-phase）
• phase --insert <after> <desc> — 途中差し込み（旧 insert-phase）
• phase --remove <N> — 削除＋リナンバー（旧 remove-phase）
• phase --edit <N> — フィールドのみ修正（番号据え置き）

Namespace メタスキル REDUX 新機構

redux では 67 個の skill を直接列挙する代わりに、6 個の namespace router をモデルに見せて 2 段階で sub-skill にルーティングします。cold-start system-prompt を ~2,150t → ~120t に削減（#2792）。各 sub-skill は引き続き /gsd:<name> で直接呼び出せます。

Namespaceキーワード タグ内包するコマンド
gsd:workflowworkflow | discuss plan execute verify phase progressdiscuss-phase, spec-phase, plan-phase, execute-phase, verify-work, phase, progress, ultraplan-phase, plan-review-convergence
gsd:projectproject lifecycle | milestones audits summarynew-project, new-milestone, complete-milestone, audit-milestone, milestone-summary, stats
gsd:qualityquality gates | code review debug audit security eval uicode-review, audit-uat, audit-fix, secure-phase, eval-review, ui-review, validate-phase, debug, forensics
gsd:contextcodebase intelligence | map graphify docs learningsmap-codebase, graphify, docs-update, extract-learnings
gsd:manageconfig workspace | workstreams thread update ship inboxconfig, workspace, workstreams, thread, pause-work, resume-work, update, ship, inbox, pr-branch, undo
gsd:ideateexploration capture | explore sketch spike spec capturecapture, explore, sketch, spike, spec-phase
surface で表示制御: /gsd:surface profile minimal でコア skill のみ surface（cold-start ~12k → ~700t）、/gsd:surface disable <cluster> で再インストールなしにクラスター単位で off にできる（#2762 の --minimal install と相補）。

スパイク & スケッチ & アイデア

IDEATE REDUX で wrap-up はフラグ化
コマンド用途主な引数
/gsd:spike技術的実現性を確認する使い捨て実験。--wrap-up で findings をスキルへ永続化、frontier モードで「次に何を spike すべきか」も提案[idea] [--quick] [--text] [--wrap-up] or frontier
/gsd:sketch使い捨て HTML モックアップで UI デザインの方向性を探索。--wrap-up で sketch findings をスキルへ永続化[design idea] [--quick] [--text] [--wrap-up] or frontier
/gsd:exploreソクラテス式対話でアイデアを練る（プラン確定前の探索）[idea]
/gsd:capture REDUX 統合アイデア・タスク・ノート・seed を行き先別にキャプチャ（旧 add-todo / note / plant-seed / add-backlog を統合）[--note | --backlog | --seed | --list] [text]
/gsd:review-backlogバックログアイテムをレビューし、アクティブマイルストーンに昇格—
使い方の流れ:
spike "idea" → 実験 → spike --wrap-up → findings がスキル化 → 本実装時に自動ロード
sketch "ui idea" → モックアップ → sketch --wrap-up → デザイン決定がスキル化 → UI 実装時に自動ロード
旧 -wrap-up サブコマンド（spike-wrap-up / sketch-wrap-up）は削除されフラグに統合。

plan-phase のエージェント構成

/gsd:plan-phase N
  ├── Phase Researcher (×4 並列)
  │    ├── Stack / Features
  │    ├── Architecture / Pitfalls
  │    └── → RESEARCH.md
  ├── Planner
  │    └── → PLAN.md (XML 構造)
  └── Plan Checker (最大 3 回ループ)
       └── PASS → 完了 / FAIL → 修正

主要フラグ:
  --tdd     → TDD モードで計画生成
  --gaps    → ギャップのみ再計画
  --reviews → 外部レビューを考慮

execute-phase のウェーブ実行

/gsd:execute-phase N
  ├── 依存関係分析
  ├── Wave 1 (独立プラン並列)
  │    ├── Executor A → commit
  │    └── Executor B → commit
  ├── Wave 2 (Wave 1 に依存)
  │    └── Executor C → commit
  └── Verifier
       └── PASS / FAIL → VERIFICATION.md

主要フラグ:
  --tdd         → TDD モードで実行
  --wave N      → 特定 wave から再開
  --interactive → 各タスク前に確認

各 Executor は新鮮な 200K コンテキストで実行。

plan-review-convergence REDUX

/gsd:plan-review-convergence N --codex --gemini
  ├── 既存 PLAN.md を外部 AI に投げる
  ├── レビュー集約 (HIGH/MED/LOW)
  ├── HIGH があれば replan
  ├── 再レビュー → 収束判定
  └── max-cycles まで繰り返し

主要フラグ:
  --codex / --gemini / --claude /
  --opencode / --ollama / --lm-studio /
  --llama-cpp     → 使う AI を指定
  --all           → 全レビュアー使用
  --max-cycles N  → 上限サイクル
  --ws <name>     → workstream 指定

spec-phase の仕様精査フロー

/gsd:spec-phase N
  ├── コードベーススカウト
  ├── ソクラテス式対話 (最大6ラウンド)
  │    └── 4次元で曖昧度スコアリング
  ├── ゲート: 曖昧度 ≤ 0.20 かつ
  │          全次元最小値を満たす
  └── → SPEC.md（偽造不可能な要件）
       └── discuss-phase が自動ロード

--auto  → 推奨デフォルトで自動決定
--text  → テキスト形式で出力

spike / sketch のフロー

/gsd:spike "アイデア"
  ├── 実験分解 → リスク順実行
  ├── 検証 → .planning/spikes/ に記録
  └── /gsd:spike --wrap-up
       └── .claude/skills/spike-findings/
            → 将来のビルドで自動ロード

/gsd:sketch "UI アイデア"
  ├── モード確認 → 2〜3バリアント生成
  ├── HTML モックアップ比較
  └── /gsd:sketch --wrap-up
       └── .claude/skills/sketch-findings/
            → UI フェーズで自動ロード

discuss-phase のフラグ

/gsd:discuss-phase N
  --auto    → 推奨デフォルトで自動決定
  --chain   → 対話後に plan+execute を自動実行
  --batch   → ファイルベース UI で質問バッチ処理
  --power   → 全質問を一括生成（自分のペースで回答）
  --all     → 全 gray area を対話的にカバー
  --analyze → 想定を分析して表示
  --text    → テキスト形式で出力

      capture / capture --note / capture --backlog / capture --seed /

判断基準:
- trivial な修正（コメント・変数名）か → fast
- 局所修正か → quick（フラグで品質調整）
- 実装前に軽い仕様確認が必要か → --discuss
- 実装アプローチを調査したいか → --research
- plan-check と verification だけほしいか → --validate
- 品質保証（全パイプライン）が必要か → --full
- 独立した新機能か → phase（新規）
- 既存ロードマップの途中に差し込む必要があるか → phase --insert
- フェーズの定義を直したいか → phase --edit
- 今すぐ実装するか、後で検討するだけか → capture (--note / --backlog / --seed)
- 何かが壊れているか → debug
- どのコマンドか迷っているか → progress --do "..."
- 次に何をすべきか不明 → progress --next
- アイデアを練りたいか → explore
- 技術的実現性を先に確認したいか → spike
- spike findings を保存したいか → spike --wrap-up
- UI デザインの方向性を先に探りたいか → sketch
- フェーズ要件が曖昧・仕様を先に固めたいか → spec-phase
- MVP の縦切りで進めたいか → mvp-phase
- AI 機能を組み込むか → ai-integration-phase
- フロントエンドフェーズか → ui-phase
- 他 AI のレビュー意見もすり合わせたいか → plan-review-convergence
- 実装完了して PR を出すか → ship
- GitHub の issues/PR を整理したいか → inbox
- 既存 ADR/PRD/SPEC から .planning/ を初期化したいか → ingest-docs

- プロダクトはすでに完成または運用段階にある
- 既存コードベースを前提に拡張・修正したい

注意点

execute-phase をやり直さない。 実装後に少し変えたいなら /gsd:quick、体系的に問題を洗いたいなら /gsd:verify-work を使う。
trivial な修正に quick を使わない。 コメント追加・変数名変更レベルなら /gsd:fast で十分。quick はサブエージェントを起動するのでコストがかかる。
旧コマンド名を使わない。 add-phase / insert-phase / remove-phase / add-todo / note / plant-seed / set-profile / settings / next / do / spike-wrap-up / sketch-wrap-up はすべて redux で統合・改名・廃止されています。v1.38→redux 移行表を参照。
  • 計画がズレていると感じたら /gsd:discuss-phase [N] を挟んでから re-plan。
  • フェーズ要件が曖昧なら /gsd:spec-phase [N] で discuss 前に仕様精査。
  • 技術的に動くか不安なら /gsd:spike で先に実験 → /gsd:spike --wrap-up で findings を永続化。
  • UI の方向性が決まっていないなら /gsd:sketch で先にモックアップ探索 → /gsd:sketch --wrap-up で設計を永続化。
  • MVP で縦切りに進めたいなら /gsd:mvp-phase [N]。SPIDR 分割 → plan-phase に橋渡し。
  • 他 AI のセカンドオピニオンが欲しいなら /gsd:plan-review-convergence [N] で自動 replan ループ。
  • セッションをまたぐなら /gsd:progress → /gsd:resume-work → /gsd:progress --next（次を自動判定）。
  • コンテキスト品質が落ちたら /clear してから /gsd:resume-work。/gsd:health --context でコンテキスト利用率を確認可（60%で警告 / 70%でクリティカル）。
  • 既存コードベースで初めて GSD を使う場合は /gsd:map-codebase → /gsd:new-project。
  • 既存の ADR/PRD/SPEC がある場合は /gsd:ingest-docs で .planning/ を自動生成（最大50ドキュメント、ADR 優先）。
  • プランが大きすぎると stub になる。タスクは 2-3 個が目安。
  • コスト削減: /gsd:config --profile budget + /gsd:config で research / plan_check をオフ。surface 制御は /gsd:surface。
  • cold-start を最小化したいなら redux インストール時に --minimal フラグ（または /gsd:surface profile minimal）。32K–128K の小規模モデル向け。
  • .planning/ をバージョン管理したくない場合は commit_docs: false + .gitignore に追加。
  • フェーズをロールバックしたいなら /gsd:undo <phase>（依存チェック付き）。
  • PR を出すときは /gsd:pr-branch で .planning/ コミットを除外したクリーンブランチを作成。
  • /gsd:ultraplan-phase BETA は Claude Code v2.1.91+ が必要。安定版は /gsd:plan-phase。
  • SDK は本体に統合済み（ADR-0174）。@gsd-build/sdk や @opengsd/gsd-sdk は不要。gsd-sdk バイナリは installer が ~/.local/bin/ に symlink。
