3 つの見分け方

  • いま着手するか？ しないなら /gsd-capture（フラグで todo/note/backlog/seed を選ぶ）。
  • 局所修正か、独立機能か？ 局所修正なら /gsd-quick（または /gsd-fast）、独立機能なら /gsd-phase。
  • 順番を壊す必要があるか？ 途中差し込みなら /gsd-phase --insert。既存編集なら /gsd-phase --edit。
quick のフラグ使い分け:
• フラグなし — 最速で実装（バグ修正・設定変更向き）
• --discuss — 事前に仕様確認してから実装
• --research — 実装アプローチを事前調査
• --validate — plan-check + verification のみ有効（discussion なし）
• --full — discussion + research + plan-check + verification すべて有効
• フラグは組み合わせ可: --discuss --research --validate = --full
fast vs quick:
• fast — サブエージェントなし・計画なし。コメント追加・変数名変更レベルの trivial な修正に。
• quick — planner + executor を起動。小〜中規模の実際の変更に。
spike vs sketch vs mvp-phase:
• spike — 技術的実現性を確認する使い捨て実験。「これは動くか？」を検証。
• sketch — UI デザインの方向性を探索する使い捨てモックアップ。「これは見えるか？」を探索。
• mvp-phase NEW — 既存フェーズを垂直 MVP スライスとして計画。「最小で価値が届くか？」を確認。
spike / sketch は --wrap-up で findings を永続スキルとして保存できる。
phase のフラグ使い分け:
• フラグなし — ロードマップ末尾に整数番号で追加（旧 add-phase）
• --insert <after> <desc> — 小数番号で途中に差し込み（旧 insert-phase）
• --remove <N> — 削除 + リナンバー（旧 remove-phase）
• --edit <N> — 任意フィールドを編集（NEW）

注意点

execute-phase をやり直さない。 実装後に少し変えたいなら /gsd-quick、体系的に問題を洗いたいなら /gsd-verify-work を使う。
trivial な修正に quick を使わない。 コメント追加・変数名変更レベルなら /gsd-fast で十分。quick はサブエージェントを起動するのでコストがかかる。
plan-review-convergence は feature gate あり。 workflow.plan_review_convergence=true を /gsd-config --advanced で有効化してから使う。デフォルトは off。
  • 計画がズレていると感じたら /gsd-discuss-phase [N] を挟んでから re-plan。
  • 計画前に Claude の想定アプローチだけ確認したいなら /gsd-discuss-phase N --assumptions（旧 list-phase-assumptions）。
  • フェーズ要件が曖昧なら /gsd-spec-phase [N] で discuss 前に仕様精査。
  • 最小で価値を届ける構造にしたいなら /gsd-mvp-phase [N] でユーザーストーリー + SPIDR 分割。
  • 技術的に動くか不安なら /gsd-spike で先に実験。/gsd-spike --wrap-up で findings を永続化。
  • UI の方向性が決まっていないなら /gsd-sketch で先にモックアップ探索。/gsd-sketch --wrap-up で設計を永続化。
  • セッションをまたぐなら /gsd-progress → /gsd-resume-work → /gsd-progress --next。
  • コンテキスト品質が落ちたら /clear してから /gsd-resume-work。
  • 既存コードベースで初めて GSD を使う場合は /gsd-map-codebase --fast → /gsd-map-codebase → /gsd-new-project。
  • 既存の ADR/PRD/SPEC がある場合は /gsd-ingest-docs で .planning/ を自動生成（ADR優先）。
  • プランが大きすぎると stub になる。タスクは 2-3 個が目安。
  • コスト削減: /gsd-config --profile budget + /gsd-config で research / plan_check をオフ。
  • アップデート後にローカル変更が消えたら /gsd-update --reapply。
  • マルチランタイムを使っているなら /gsd-update --sync でスキルを同期。
  • コンテキストが圧迫されたら /gsd-surface profile core（v1.42 NEW）。クラスタ単位で /gsd-surface disable <cluster>。状態は ~/.claude/skills/.gsd-surface.json。
  • ADR 駆動で開発しているなら /gsd-plan-phase N --ingest "docs/adr/*.md" で discuss-phase をスキップ可能（v1.42 NEW）。
  • .planning/ をバージョン管理したくない場合は commit_docs: false + .gitignore に追加。
  • フェーズをロールバックしたいなら /gsd-undo <phase>（依存チェック付き）。
  • PR を出すときは /gsd-pr-branch で .planning/ コミットを除外したクリーンブランチを作成。
  • /gsd-ultraplan-phase BETA は Claude Code v2.1.91+ が必要。安定版は /gsd-plan-phase。
  • /gsd-plan-review-convergence BETA は外部 AI CLI（codex / gemini / opencode）または local LLM サーバー（ollama / lm-studio / llama-cpp）が必要。
