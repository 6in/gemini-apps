GSD コマンド チートシート

meta-prompting & context engineering による spec-driven 開発システム。
既存プロダクトの保守・拡張を前提に、どのコマンドで始めるかをすぐ判断できるように全 32 コマンドを整理。

まずはこれで判定

今すぐ実装しない → /gsd:add-todo
今やる小変更 → /gsd:quick
小さいが先に少し仕様確認したい → /gsd:quick --discuss
小さいが品質保証もほしい → /gsd:quick --full
独立した新機能を末尾に追加 → /gsd:add-phase
既存計画の途中に urgent work を差し込む → /gsd:insert-phase [N]
phase の方針が曖昧 → /gsd:discuss-phase [N] → /gsd:plan-phase [N]
何かが壊れた → /gsd:debug [desc]

3つの見分け方

  • いま着手するか？ しないなら add-todo。
  • 局所修正か、独立機能か？ 局所修正なら quick、独立機能なら add-phase。
  • 順番を壊す必要があるか？ 途中差し込みなら insert-phase。
quick のフラグ使い分け:
• --discuss — 事前に軽く仕様確認してから実装
• --full — plan-check + verification 付き（品質重視）
• フラグなし — 最速で実装（バグ修正・設定変更向き）
add-phase vs insert-phase:
• add-phase — ロードマップ末尾に整数番号で追加。今の流れを壊さない。
• insert-phase — 途中に小数番号（例: 3.1）で差し込み。後続を renumber しない。

plan-phase のエージェント構成

/gsd:plan-phase N
  ├── Phase Researcher (×4 並列)
  │    ├── Stack / Features
  │    ├── Architecture / Pitfalls
  │    └── → RESEARCH.md
  ├── Planner
  │    └── → PLAN.md (XML 構造)
  └── Plan Checker (最大 3 回ループ)
       └── PASS → 完了 / FAIL → 修正

execute-phase のウェーブ実行

/gsd:execute-phase N
  ├── 依存関係分析
  ├── Wave 1 (独立プラン並列)
  │    ├── Executor A → commit
  │    └── Executor B → commit
  ├── Wave 2 (Wave 1 に依存)
  │    └── Executor C → commit
  └── Verifier
       └── PASS / FAIL → VERIFICATION.md

各 Executor は新鮮な 200K コンテキストで実行。メインウィンドウは 30-40% に留まる。

判定プロンプト

この変更に対して、GSD のどのコマンドで始めるべきか判定してください。
候補: quick / quick --discuss / quick --full / add-phase / insert-phase / add-todo / discuss-phase / debug

判断基準:
- 局所修正か
- 実装前に軽い仕様確認が必要か
- 品質保証（plan-check / verification）が必要か
- 独立した新機能か
- 既存ロードマップの途中に差し込む必要があるか
- 今すぐ実装するか、後で検討するだけか
- 何かが壊れているか

前提:
- プロダクトはすでに完成または運用段階にある
- 既存コードベースを前提に拡張・修正したい

HTML 再生成プロンプト

最新の GSD 公式ドキュメントと最新リリースを参照して、single HTML のチートシートを 1 ファイルで生成してください。

要件:
- 出力は self-contained な single HTML
- 外部 CSS / JS / フォントに依存しない
- 日本語で記述
- ダーク / ライトの両方で読みやすい
- 以下を必ず含める:
  1. GSD の全コマンド早見表（コア / フェーズ管理 / セッション / ユーティリティ）
  2. quick / quick --discuss / quick --full / add-phase / insert-phase / add-todo / discuss-phase の使い分け
  3. add-phase と insert-phase の違い
  4. execute-phase を再実行せず quick / verify-work を使うべき注意点
  5. ワークフロー全体像とエージェント構成図
  6. 設定リファレンス（config.json / モデルプロファイル / Git ブランチ戦略）
  7. 既存プロダクト保守・CLI 拡張向けの実例
  8. コピーボタン付きの判定プロンプト
  9. 出典セクション
- 表とカード UI を使って見やすくする
- 印刷しても読めるようにする

情報源の優先順位:
1. gsd-build/get-shit-done の README
2. docs/USER-GUIDE.md
3. 最新 release notes
4. commands/gsd/*.md の各コマンド定義

ファクト要件:
- コマンド用途や使い方は公式情報に合わせる
- quick の --discuss / --full フラグを反映する
- add-phase は roadmap 末尾への整数番号追加、insert-phase は途中への小数番号差し込みとして説明する
- add-todo は capture only で、実装開始コマンドとして扱わない
- 既存コードベースの文脈では map-codebase → new-project に触れる
- validate-phase / add-tests / cleanup / reapply-patches など新コマンドも含める

出力形式:
- まず HTML 本文のみを返す
- markdown の前置きや説明文は不要

注意点

execute-phase をやり直さない。 実装後に少し変えたいなら /gsd:quick、体系的に問題を洗いたいなら /gsd:verify-work を使う。
  • 計画がズレていると感じたら /gsd:discuss-phase [N] を挟んでから re-plan。
  • セッションをまたぐなら /gsd:progress または /gsd:resume-work。
  • コンテキスト品質が落ちたら /clear してから /gsd:resume-work。
  • 既存コードベースで初めて GSD を使う場合は /gsd:map-codebase → /gsd:new-project の流れ。
  • プランが大きすぎると stub になる。タスクは 2-3 個が目安。
  • コスト削減: /gsd:set-profile budget + /gsd:settings で research / plan_check をオフ。
  • アップデート後にローカル変更が消えたら /gsd:reapply-patches。
  • .planning/ をバージョン管理したくない場合は commit_docs: false + .gitignore に追加。

    pending/              # キャプチャ済みアイデア
    done/                 # 完了した todo
  debug/                  # アクティブなデバッグセッション
    resolved/             # 解決済みデバッグセッション
